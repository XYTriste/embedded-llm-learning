## 第 0 站 · 模型文件到底是什么？

**设问**：一个 15 GB 的 FP16 模型文件，每一个字节存的是什么？

先算一笔账。Qwen2.5-7B 有 **7.6156 B（76 亿）个参数**——就是 76 亿个数字。FP16 每个数字占 2 字节：

```
7.6156e9 × 2 B ≈ 15.2 GB
```

而你硬盘上 FP16 文件的真实大小是 15,237,853,600 字节。账完全对上。

**结论（第一块基石）**：模型文件 = 一张超大号的数字表格 + 一小本"说明书"。没有魔法。量化、部署、推理框架的所有事情，都是在回答"怎么存这张表"和"怎么用它算账"两个问题。

## 第 1 站 · 量化的本质：用"整数 + 尺子"代替浮点

**设问**：4 bit 只能表示 0~15 这 16 个整数，怎么装下 0.0013？怎么装下 −2.7？

答案分两步。

**第一步：给小数配一把尺子（scale）。** 不存小数本身，存"它是某个最小单位的多少倍"：

```
x ≈ Δ · q        其中 q ∈ {0, 1, ..., 15}，Δ 是"一格的宽度"
```

比如 Δ = 0.001，那么 q = 13 就表示 0.013。这就是**定点数**的思想：整数 + 一把共用的尺子。

**第二步：让尺子会平移（min / zero-point）。** 上面的尺子只能表示 0 到 15Δ 的正数。给尺子加一个平移量：

```
x ≈ Δ · q − m        m 是"零点偏移"
```

q 仍然只有 0~15，但通过 m 平移，可表示的范围变成 [−m, 15Δ−m]，负数自然出现。**注意一个教学要点：4 bit 里存的 q 是"无符号的格子序号"，正负号信息完全藏在 min 这个平移量里。**

**几何直觉**：把连续数轴切成 16 格，量化就是"四舍五入到最近的格线"。量化误差最大是半格（Δ/2）。格子越细（Δ 越小），误差越小——但需要的"格数"就越多，这就是为什么 bit 数不能无限砍。

**存储账**：FP16 用 16 bit 存一个数，Q4 用 4 bit → 体积 1/4。76 亿参数 × 0.5 B = **3.81 GB**。但我们实际看到的是 4.7 GB。多出来的 0.9 GB 去哪了？带着这个问题去第 4 站。

## 第 2 站 · 一把尺子量全世界？——分组量化

**设问**：假设一整层几万个权重共用一把尺子，会发生什么？

权重的真实分布是**中间密、两头疏**的钟形：绝大多数权重挤在 0 附近，少量离群值跑到 ±3 以外。共用一把必须覆盖离群值的大尺子，后果是：**大量程 ÷ 16 格 = 每格很宽**，挤在 0 附近的绝大多数权重全落在同一两格里——它们的差异被抹平，相对误差爆炸。

**解决：分组，每组配一把贴身小尺子。** 把几万个权重切成若干小组，每组单独算自己的 min/max、配自己的 Δ 和 m。小组内数值范围窄，格子细，误差小。

几何图像：与其用一条直线勉强拟合一条弯曲的曲线，不如**分段**——段数越多，每段越贴身，逼近越准。分组量化就是"分段线性逼近"权重分布。

**代价（天下没有免费午餐）**：每组都要把尺子本身（Δ、m）存下来。这就是量化格式的**额外开销（overhead）**，也是"4 bit 格式实际占 4.5~6 bit"的原因。分组越细越准、开销越大——量化格式的进化史，就是在这条曲线上不断找更优的位置。

## 第 3 站 · GGUF：文件的"户口本 + 目录"

**设问**：一个文件既要装 76 亿个数字，又要让推理程序知道"这些数字是什么、按什么顺序读、词表长什么样"，该怎么组织？

GGUF 就是答案。它是 llama.cpp 作者的第四代容器格式（GGML → GGMF → GGJT → GGUF；名字是个社区玩笑，常被戏称 "GPT-Generated Unified Format"）。我们对真实文件解析出的结构：

```
┌─ 文件头 ──────────────────────────────┐
│ magic: "GGUF"（4 字节，校验用暗号）       │
│ version: 3                           │
│ tensor_count: 339（这个数字表格有几行）    │
│ metadata_kv_count: 34（说明书有几条）     │
├─ metadata（说明书，34 条键值对）─────────┤
│  general.architecture = qwen2         │
│  general.name = Qwen2.5 7B Instruct   │
│  qwen2.context_length / embedding长度… │
│  tokenizer.ggml.tokens（15 万个词）…    │
│  tokenizer.chat_template（聊天模板）     │
│  general.file_type = 15 (=Q4_K_M)      │
├─ tensor info 表（目录，339 条）──────────┤
│  名字 / 形状 dims / 类型 / 在数据区的偏移  │
├─ 数据区（按 32 字节对齐）────────────────┤
│  339 个 tensor 的字节，一行挨一行          │
└───────────────────────────────────────┘
```

前 8 条真实目录长这样：

| 名字 | 形状 | 类型 | 元素数 |
|---|---|---|---|
| token_embd.weight | [3584, 152064] | Q4_K | 5.45 亿（词表嵌入） |
| blk.0.attn_norm.weight | [3584] | F32 | 3,584（归一化，不量化！） |
| blk.0.ffn_down.weight | [18944, 3584] | **Q6_K** | 6,790 万 |
| blk.0.ffn_gate.weight | [3584, 18944] | Q4_K | 6,790 万 |
| blk.0.ffn_up.weight | [3584, 18944] | Q4_K | 6,790 万 |
| blk.0.ffn_norm.weight | [3584] | F32 | 3,584 |
| blk.0.attn_k.bias | [512] | F32 | 512（偏置，不量化！） |
| blk.0.attn_k.weight | [3584, 512] | Q4_K | 184 万 |

三个立刻能读出的信息：
1. **归一化层和偏置保持 F32 原精度**——它们总共只有 0.3M 个元素，占 0.001 GB，不值得量化，量化了反而伤训练稳定性。
2. 339 = 1 嵌入 + 28 层 × 12 个左右 + 输出头 + norm。**模型架构是一眼可读的**。
3. 头部 + 说明书总共 5.95 MB，占文件 0.13%。**99.87% 的字节都是权重数字**——回到第 0 站的结论。

## 第 4 站 · Q4_K_M 逐字节解剖（核心一站）

### 4.1 先看全局：4.7 GB 的配方

真实文件的类型直方图：

| 类型 | tensor 数 | 元素数 | 字节 | 折算 bit/权重 |
|---|---|---|---|---|
| Q4_K | 169 | 60.9 亿 | 3.428 GB | **4.50** |
| Q6_K | 29 | 15.2 亿 | 1.248 GB | **6.56** |
| F32 | 141 | 0.03 亿 | 0.001 GB | 32 |

验算：Q4_K 每权重 144 B/256 = **4.5 bit** → 60.94 亿 × 4.5/8 = 3.428 GB，分毫不差。Q6_K 210 B/256 = 6.56 bit → 15.21 亿 × 6.56/8 = 1.248 GB，又对上了。**第 1 站"多出来的 0.9 GB"之谜解开：4.68 GB 总量 ÷ 76 亿参数 = 平均 4.91 bit/权重——因为 20% 的参数（15.2 亿）用了更精细的 Q6_K 尺子。**

### 4.2 Q4_K 块结构：144 字节装 256 个权重

Q4_K 以 **256 个权重为一个 super-block**，每块 144 字节：

```
┌─ Q4_K super-block（144 B = 1152 bit，摊 4.5 bit/权重）─────────┐
│ d    : FP16，2 B   —— super-block 总比例尺（一把大尺子）          │
│ dmin : FP16，2 B   —— super-block 总平移量                       │
│ scales: 8 × 6 bit = 6 B  —— 8 个子块各自的"小比例尺"（量化的量化）│
│ mins  : 8 × 6 bit = 6 B  —— 8 个子块各自的"小平移量"（同上）      │
│ qs    : 256 × 4 bit = 128 B —— 256 个权重各自的格子序号           │
└──────────────────────────────────────────────────────────────┘
```

层级结构：256 个权重分成 **8 个子块 × 32 个**。每个子块有自己的小尺子（scale 6bit、min 6bit），8 把小尺子再由 d / dmin 两把"大尺子"统一缩放。解码公式：

```
w = d · scale_j · q − dmin · min_j        （j = 该权重所属子块编号，q ∈ [0,15]）
```

**设问**：小尺子本身也是数字，存它们不亏吗？为什么还要再把它们压成 6 bit（"量化的量化"）？

答：亏 14 字节换 256 个权重各得贴身小尺子，大赚。而且小尺子只有 8 个、值域小，6 bit 足够；它们的误差会被 d 再缩放一次，对最终权重的影响可忽略。整套设计是一个**精心配平的杠杆系统**：误差大头由 4 bit 的 q 承担（反正它格子最多），精度保障交给分层的小尺子。

### 4.3 现场解码：你的模型的真实字节

从 `blk.0.ffn_gate.weight` 数据区开头读出第一个 super-block：

```
d    = 0.000106      dmin = 0.000725
8 个子块 scale = [47, 50, 44, 63, 51, 45, 47, 47]
8 个子块 min   = [40, 52, 49, 39, 63, 47, 43, 58]
前 16 个 q（低半字节）= [7, 2, 1, 7, 2, 7, 4, 3, 9, 6, 3, 4, 15, 7, 7, 7]
```

手算第一个权重：

```
w₀ = d·scale₀·q₀ − dmin·min₀
   = 0.000106 × 47 × 7 − 0.000725 × 40
   = 0.034874 − 0.029
   ≈ +0.0059
```

全部 16 个解码结果：[0.006, −0.019, −0.024, 0.006, −0.019, 0.006, −0.009, −0.014, 0.016, 0.001, −0.014, −0.009, 0.046, 0.006, 0.006, 0.006]——典型的 FFN 门控权重量级。76 亿个权重，每一个都能用这条公式从你的硬盘里还原出来。

### 4.4 "K" 和 "M" 各是什么意思

- **K**：这类分层 super-block 量化叫 **k-quants**，2023 年由 llama.cpp 社区作者 ikawrakow 提出（K 取自他的 ID）。与老式 Q4_0（整块只用一把尺子）相比，k-quants 用"大尺子套小尺子"把同样 4 bit 的误差降了一个档次。
- **M** = Medium，**混合精度配方**。看直方图：169 个 tensor 用 Q4_K，但 `ffn_down.weight`（28 个）和输出头等 29 个用了 Q6_K。

**设问**：凭什么 ffn_down 搞特殊？

**敏感性分层**：ffn_down 是 FFN 的最后一步，它的输出直接残差流回主干；输出头（lm_head）的数值直接决定 logits。这些"一错就直接传到输出"的矩阵对误差最敏感，给它们换更精细的 6.56 bit 尺子，换来的质量提升远比平均分摊划算。这就是 **Q4_K_M 的 M：不是一视同仁，而是把钱花在刀刃上**。同系列还有 Q4_K_S（更省、更糙）和 Q4_K_L（更精细）。

## 第 5 站 · 回到你的实测：数据闭环

现在你有能力重新理解三个实测现象了：

1. **文件体积**：fp16 15.2 GB → Q8_0 8.1 GB（8.5 bit/权重）→ Q4_K_M 4.7 GB（4.91 bit/权重）。每一档都能用"bit/权重 × 76 亿"算出来。
2. **生成速度**：自回归生成是**显存带宽瓶颈**——每生成 1 个 token 都要把全部激活权重从显存过一遍。体积比 15.2 : 8.5 : 4.9 ≈ 速度比（Q4 110+ t/s > Q8 70 t/s）。这解释了同机 1.6× 差距，也预测了 **fp16 在本机不会更快**——尽管它最精确。
3. **乔峰题在 Q4/Q8 上同错**：量化只动了权重的低 3~4 位精度，知识是"哪个人物"这种离散事实，存在权重的大结构里——精度损失碰不到它。错误在底座模型，与量化无关。第三次复现，结案。
