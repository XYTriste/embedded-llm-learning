## 2. 编译：四步

**必须用 PowerShell**（开始菜单搜 PowerShell），不要用 Git Bash——CMake 的 MinGW 生成器遇到 PATH 里的 `sh.exe`（Git 自带）可能错乱。

```powershell
# 第 1 步：准备环境（只对本窗口有效）
$env:Path = "C:\Users\USER\devtools\winlibs\mingw64\bin;C:\Users\USER\devtools\cmake-3.31.6-windows-x86_64\bin;" + $env:Path
$env:PROCESSOR_ARCHITECTURE = "AMD64"    # 保险丝：确保 CPU 架构识别正确
cd C:\Users\USER\dev\llama.cpp

# 第 2 步：配置（生成编译图纸，不编译）
cmake -B build -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release -DGGML_NATIVE=ON -DLLAMA_CURL=OFF "-DCMAKE_C_FLAGS=-D_WIN32_WINNT=0x0A00" "-DCMAKE_CXX_FLAGS=-D_WIN32_WINNT=0x0A00"

# 第 3 步：编译（i3 约 10~20 分钟）
cmake --build build --parallel 8

# 第 4 步：验证
.\build\bin\llama-cli.exe --version
```

**参数逐个记**：`-B build` 图纸放 build 子目录；`-G "MinGW Makefiles"` 图纸格式；`-DCMAKE_BUILD_TYPE=Release` 发布版（-O3 优化）；`-DGGML_NATIVE=ON` 针对本机 CPU 生成指令（AVX2 等，直接决定内核效率）；`-DLLAMA_CURL=OFF` 关掉联网下载，免得找本机没有的 curl 库；`-D_WIN32_WINNT=0x0A00` **目标系统声明为 Windows 10**。

**踩坑清单（全是实测）**：
1. `GGML_SYSTEM_ARCH: UNKNOWN` → 会退回无 AVX2 的 GENERIC 慢速内核。对策：上面第 1 步的保险丝 + 配置输出必须核对 `GGML_SYSTEM_ARCH: x86`
2. `cpp-httplib` 报 `'CreateFile2' has not been declared` → MinGW 默认假装给 Win7 编程（`_WIN32_WINNT=0x0601`），系统头文件把 Win8+ API 藏起来了 → 加 `-D_WIN32_WINNT=0x0A00` 放行
3. `UI: download ... Timeout` + `building without an embedded UI` → 想顺手下载网页 UI 失败，**自动跳过无害**——但后果是 `llama-server` 没有内置网页界面，只能调 API（见第 5 节）
4. OpenSSL not found 警告 → 无害（联网功能已关）

## 3. 推理：llama-cli 与线程扫描

```powershell
.\build\bin\llama-cli.exe -m D:\llmModel\blobs\sha256-2bada8a7450677000f678be90653b85d364de7db25eb5ea54136ada5f3933730 -t 4 -n 64 -p "写一首关于秋天黄昏的七言绝句。"
```

- `-m` 模型文件（Ollama blob 无扩展名没关系，内容是标准 GGUF）；机器 B 模型在 `D:\llmModel\blobs\`，两档哈希跨机一致（内容寻址）
- 启动时 `ftype: Q4_K - Medium` = GGUF 讲义 file_type=15 的活体验证
- **协议分工（教训固化）**：测速用 `-n 32`（t/s 是稳态指标，截断不影响）；测质量必须给足 `-n`（截断会遮丑）

**线程扫描数据（第④固定题，Generation t/s）**：

| -t 2 | -t 4 | -t 8 |
|---|---|---|
| 6.1 | 7.9 | 8.2 |

**结论**：2→4 线程 +29%，4→8 仅 +4%——收益断崖递减 = **内存带宽饱和的亲手直接证据**（算力瓶颈应近线性）。由此确立端侧优化第一杠杆：**量化（减每 token 字节数）而非调线程**。Q4/Q8 实测比 8.2/5.6≈1.46× vs 理论 1.6×（后台负载未清零，吻合可接受）。干净环境 llama-cli 7.9~8.2 t/s vs Ollama 9.44 → "Ollama = llama.cpp + 封装"验证成立。

## 4. 亲手量化：llama-quantize + 自工具验尸

```powershell
# 从 Q8 强转 Q4_K_M（需 --allow-requantize，否则拒绝二次量化）
.\build\bin\llama-quantize.exe D:\llmModel\blobs\sha256-3603045b543e1c0dfb27f126a3642e7f805e480b84c4781e3d848ace971cba7a D:\llmModel\my-q4_k_m.gguf Q4_K_M --allow-requantize
```

**验尸（自写 [parse-gguf](../scripts/parse-gguf.py)）**：file_type=15 · 339 tensor · Q4_K×169(3.428GB)+Q6_K×29(1.248GB)+F32×141 · 文件 4,683,073,952 字节——**与官方逐项一致，唯独 SHA256 不同**（官方 2bada8a74…，本文件 65db2780…）。

**两条核心认知**：
1. **尺寸由架构+配方决定，内容由源数值决定**——同工具同配方 ⇒ 解剖必然相同；源不同（官方 FP16→Q4，本机 Q8→Q4）⇒ 血肉必然不同。"文件大小一样 ≠ 模型一样"，大小只承诺结构。复现法结案了"官方文件怎么来的"。
2. **二次量化近免费**：量化误差按平方和合成 $\sqrt{e_1^2+e_2^2}$，Q8 自身误差 ~0.4% 被 Q4 步长 2~3% 淹没（2.00%→2.02%）。`allow-requantize` 的警告是保守默认。**实测验证**：官方 vs 亲手文件同题对照（乔峰题皆错且错法各异、水池题皆对且骨架同构、速度 within 噪声）——"手头只有 Q8 时直接再量化到 Q4"是可行工程路径。想看真·胡言乱语须压到 Q2_K 级。

## 5. 服务化：llama-server（下一站，在家完成）

```powershell
# 窗口 1：起服务（常驻，勿关）
.\build\bin\llama-server.exe -m D:\llmModel\my-q4_k_m.gguf -t 4 --port 8080

# 窗口 2：调 OpenAI 兼容 API
Invoke-RestMethod -Uri http://localhost:8080/v1/chat/completions -Method Post -ContentType "application/json" -Body '{"messages":[{"role":"user","content":"写一首关于秋天黄昏的七言绝句"}],"temperature":0.7}'
```

- `/v1/chat/completions` 即 OpenAI 兼容格式——Ollama 暴露的同款接口。**接口规范是可移植的**：将来客户端（含教务助手）换底层引擎只改 IP 端口，代码不动（对比：线程数不可移植）
- llama-server = llama-cli 包成 HTTP 服务；Ollama ≈ llama-server + 模型管理 + 聊天模板 + 常驻
- 因第 2 节踩坑 3（UI 资源未嵌入），浏览器开 8080 没有聊天页面，属正常
- 教务助手架构位：RAG 检索层坐在这个 API 前面
