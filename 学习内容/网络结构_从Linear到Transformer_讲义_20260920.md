## 0. 全景地图（先记住这张图，后面每一站都在填充它）

```
token ids
   │
   ▼
token_embd.weight        查表：token → 3584 维向量
   │
   ▼
┌───────────────────────── 重复 28 次 ─────────────────────────┐
│  block i:                                                    │
│    x ──► RMSNorm ──► Q/K/V 三个 Linear ──► 多头注意力 ──► O    │
│    │                                            │            │
│    └─────────────── 残差相加 ◄──────────────────┘            │
│    │                                                         │
│    ▼                                                         │
│    RMSNorm ──► FFN(gate / up / down 三个 Linear)             │
│    │                                                         │
│    └─────────────── 残差相加 ◄────────────────── 输出          │
└──────────────────────────────────────────────────────────────┘
   │
   ▼
output_norm ──► output.weight ──► logits(15.2万维) ──► 取下一个 token
```

一句话版本：**查表得到向量 → 同一栋楼重复爬 28 层 → 输出头给出 15 万个候选的得分**。

模型四个关键尺寸（全部来自你的 GGUF 说明书）：

| 尺寸 | 值 | 含义 |
|---|---|---|
| embedding_length | 3584 | 每个 token 的向量长度，全模型的"主干道宽度" |
| block_count | 28 | 那栋楼重复 28 次 |
| context_length | 32768 | 最多同时看多少个 token |
| feed_forward_length | 18944 | FFN 内部的加宽尺寸 |

## 1. 第一站：token_embd.weight [3584, 152064]——查表，不是矩阵乘法

**设问**：一个 token（比如"梯"）进入网络的第一步是什么？

不是算，是**查表**。`token_embd` 是一张 152,064 行 × 3584 列的表：每一行是一个 token 的"身份证向量"。程序拿到 token 编号，直接按行号取出对应的 3584 维向量。

> 这就是为什么它没有尺度问题、用 Q4_K 量化也关系不大——它不参与连续运算，只是检索。（对比后面 ffn_down 的敏感性，回头看第 5 节。）

152,064 = 词表大小（qwen2.5 的 BPE 分词器切出来的全部 token）；3584 = 主干道宽度。

---

## 2. 第二站：一个 block 的骨架——残差 + 归一化

28 层楼长得一模一样，每层楼由**两大件**组成：注意力（attention）和前馈网络（FFN），中间用两件"连接件"缝起来：

```
x ──► [归一化] ──► [注意力] ──► + ──► [归一化] ──► [FFN] ──► + ──► 传给下一层
│                  （大件1）    ▲                （大件2）     ▲
└───────────────────────────────┘ └────────────────────────────┘
              残差连接（把原路加回来）
```

**归一化（你文件里的 `attn_norm.weight`、`ffnn_norm.weight`，各 3584 个数、F32）**：
就是 RMSNorm——把向量除以自己的均方根，再乘一个可学习的 3584 维系数向量 g。作用：把每层的数值规模钉在稳定区间，让 28 层堆叠不会数值爆炸/消失。你 metadata 里的 `layer_norm_rms_epsilon` 就是它的小数稳定性保护。它只有 3584 个数，所以不量化、用 F32。

**残差连接**：`注意力输出 + 原始输入`。你学过梯度消失——残差就是给梯度修的一条"高速公路"：输出对输入的导数恒 ≥1。没有它，28 层根本训不动。

## 3. 第三站：注意力——Q/K/V 三把 Linear + 多头检索

这是全模型唯一真正"新"的结构，但拆开了还是 Linear。

**设问**：模型要决定下一个词，本质上在做什么？——**在已看到的上下文里检索"接下来最可能跟谁"**。注意力就是把"检索"写成可微分的矩阵运算。

### 3.1 Q/K/V：三把形状不同的 Linear

| tensor | 形状（存法：[输入维, 输出维]） | 干什么 |
|---|---|---|
| attn_q.weight | 3584 → 3584 | 每个 token 问自己："我要找什么？" |
| attn_k.weight | 3584 → 512 | 每个 token 挂门牌："我是什么" |
| attn_v.weight | 3584 → 512 | 每个 token 备一份"我被用到时提供的信息" |

流程：x（3584 维）分别过三把 Linear，得到 q、k、v 三个向量。然后**每个 token 的 q 去和前面所有 token 的 k 算相似度**（点积，你 RL 里的打分），softmax 归一成权重（你对 softmax 很熟——策略梯度里那个），再加权平均所有 v——检索完成。

```
attention(q,k,v) = softmax(q·kᵀ / √128) · v
```

几何图像：q 是一根探针，k 是满屋子挂的门牌，点积=匹配度，v 是匹配成功后要取走的货。

### 3.2 多头：28 个头并行检索

3584 拆成 28 组、每组 128 维——相当于同时派 **28 个不同的探针**各自检索（一个头盯语法、一个头指代、一个头话题……学出来的分工）。q 有 28 个头，所以 Q 矩阵是满的 3584→3584。

### 3.3 GQA：K/V 只有 4 个头——为部署而生的设计

你的说明书里有两个数：`head_count = 28`，`head_count_kv = 4`。K/V 只有 4 个头，**28 个 q 头共享这 4 组 K/V**（Grouped-Query Attention）。

**设问**：凭什么 K/V 可以抠门？——因为解码时要**缓存**所有历史 token 的 K/V（这就是 KV cache）。头越少，缓存越小、带宽越省。代价是质量轻微下降，实测划算。这是端侧部署的核心优化点，也是你做实验时 `prompt eval cached` 那行字背后的实体。

### 3.4 O：注意力输出投影

28 个头检回来的货拼回 3584 维，再过一把 `attn_output.weight`（3584→3584）的 Linear 混匀，残差相加，进入 FFN。

## 4. 第四站：FFN——门控三件套

| tensor | 形状 | 干什么 |
|---|---|---|
| ffn_gate.weight | 3584 → 18944 | 升维，并打分：哪些特征该通过 |
| ffn_up.weight | 3584 → 18944 | 升维，提供特征内容 |
| ffn_down.weight | 18944 → 3584 | 压回主干道 |

计算：$\text{FFN}(x) = W_{down}\big(\,\text{silu}(W_{gate}x) \odot (W_{up}x)\,\big)$

一个 Linear 升维到 18944（≈5.3 倍宽），**两个**分支：gate 像"闸门"决定每个通道放不放行，up 是内容，逐元素相乘后再由 down 压回 3584。

**几何图像**：注意力是"跨 token 交流"，FFN 是"每个 token 关起门来思考"——在 18944 维的超宽工作台上把信息重组一遍。两道工序交替 28 次。

**为什么 ffn_down 用 Q6_K（呼应上一讲）**：down 的输出直接加回残差主流，它的误差会流进后面所有层——敏感性在这条链上最高。

---

## 5. 第五站：收尾三件套 + 参数总量验算

- `output_norm.weight`：最后一道 RMSNorm。
- `output.weight` [3584, 152064]：输出头，一把大 Linear——3584 维状态向量 → 15.2 万个 logits（每个 token 一个得分）。它是全模型对误差最敏感的地方（直接变成概率），所以配 Q6_K。
- softmax + 采样：logits 归一化成概率，按 temperature 抽下一个 token。temperature>0 就是你诗题实验里"同一题出两首诗"的来源。

**参数总量验算**（和 GGUF 解析出的 7.6156 B 对账）：

| 部件 | 每块参数 | 说明 |
|---|---|---|
| attn_q | 12,845,056 | 3584×3584 |
| attn_k + attn_v | 3,670,016 | 2×(3584×512)，GQA 省出来的 |
| attn_output | 12,845,056 | 3584×3584 |
| FFN 三件 | 203,685,888 | 3×(3584×18944)，**占绝对大头** |
| 每 block 合计 | ≈233,057,792 | × 28 = 6.526 B |
| token_embd | 544,997,376 | 152064×3584 |
| output.weight | 544,997,376 | 同上 |
| 合计 | **≈7.6156 B** | ✓ 与文件解析一致 |

**tensor 数验算**：1（embd）+ 28×12（每块：q/k/v 三 weight+三 bias、o、两 norm、FFN 三件）+ 1（output_norm）+ 1（output）= **339** ✓ 与 `tensor_count` 一致。

## 6. 第六站：一个 token 的完整旅程（串起你所有的实测）

生成阶段的一步（对应你看到的 ~14 ms/token @ 70 t/s）：

1. 新 token 查表 → 3584 维向量
2. 过 28 个 block：每个 block 把**全部权重读一遍**做两次 Linear 系运算（这就是"带宽瓶颈"的实体——7.6B 参数 × 4.91 bit ÷ 显存带宽 = 每 token 时间）
3. 输出头 → 15.2 万 logits → 采样出下一个 token
4. 循环

而 prompt 阶段把 557 个 token 排成矩阵**并行**过同样的路——权重只读一次，所以 5068 t/s。

KV cache 的大小也能算了：每 token 每 block 存 K+V = 2×(4头×128维)×2B = 2 KB，×28 block ≈ **57 KB/token**——上下文 8K 就要 470 MB 显存。这就是为什么端侧部署要连 KV cache 一起量化，也是 GQA 的价值所在。
